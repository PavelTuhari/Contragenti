1. Общие положения

1.1. Цель

Получить единый контур «от обращения клиента до денег и отгрузки»: лиды и сделки → договор и спецификация → производственный заказ → операции и загрузка участков → склад готовой продукции → отгрузка и доставка → счёт, оплата, закрытие. Все службы работают в одной базе, каждый видит свой раздел, руководство — сводку в реальном времени. Контрагенты заводятся из государственного реестра date.gov.md без ручного ввода реквизитов.

1.3. Границы

  • Бухгалтерский учёт (проводки, баланс, налоговая отчётность) остаётся в учётной системе Заказчика (1С / una.md); CRM-контур поставляет ей первичные документы и получает статусы оплат (§3).
  • Расчёт зарплаты, кадры, охрана труда — вне объёма.
  • Конструкторская документация (CAD) — вне объёма; в системе хранятся ссылки на файлы и версии.

2. Блок 1 — требования владельцев бизнеса

Что хочет владелец

Видеть предприятие «одним экраном» и понимать, где теряются деньги и время: сколько денег в работе, кто должен, что запаздывает, какая маржа у заказов и проектов, загружено ли производство на месяц вперёд. Управлять не по звонкам мастерам, а по цифрам, которые обновляются сами.

Требования

OWN-01MUSTРабочий стол руководителя — плитки этапов «от контракта до денег» из прототипа (Предложение → Переговоры → Готово к заказу → Ожидает аванс → В работе → Готово к отгрузке → Отгружено/ждём оплату → Закрыто) с количеством, суммой и просрочкой; клик открывает раздел с тем же фильтром. Добавить плитки: Просроченная дебиторка, Загрузка производства на 30 дней (%), Маржа месяца, Готовая продукция на складе (сумма).

OWN-02MUSTПлан-факт по месяцу и кварталу: выручка, отгрузки, поступления, новые сделки, конверсия воронки; план вводится по отделам, факт считается из документов.

OWN-03MUSTМаржинальность заказа и проекта: цена продажи − материалы (BOM, §5) − нормо-часы по ставкам участков − доставка; красная подсветка при марже ниже порога; порог — настройка.

OWN-04MUSTУтверждения: скидка выше порога, отгрузка при долге клиента выше лимита, изменение цены после подписания спецификации — требуют одобрения руководителя (кнопка «Утвердить» в списке ожиданий, уведомление в Telegram/e-mail).

OWN-05MUSTРолевая модель и аудит: каждый пользователь видит только свои разделы; любое изменение документа пишется в журнал (кто, когда, что было / стало); журнал нельзя редактировать.

OWN-06SHOULDМобильный просмотр рабочего стола и отчётов (веб-кабинет, телефон), без установки приложений.

OWN-07SHOULDЕжедневная сводка в 8:00 на e-mail/Telegram: просрочки, деньги за вчера, заказы к отгрузке сегодня, задачи без исполнителя.

OWN-08NICEПрогноз денежного потока на 8 недель по срокам оплат в договорах и спецификациях.

Критерии приёмки

  • На демо-данных все плитки рабочего стола непустые (правило AGENTS.md §1 п.5 прототипа), суммы плиток совпадают с отчётом «Процесс исполнения заказов» с точностью до копейки.
  • Маржа заказа из демо-набора считается и совпадает с ручным расчётом по BOM и операциям (тест-кейс в DML-тесте).
  • Попытка отгрузить клиенту с долгом выше лимита без утверждения — отказ с сообщением в строке сообщений (не модальное окно), запись в журнале.

3. Блок 2 — требования бухгалтерии

Что хочет бухгалтерия

Ни один документ не вводится дважды: реквизиты контрагента — из реестра, счета и накладные — из заказов, оплаты — из выписки банка, а в учётную систему всё уходит пакетом с контрольными суммами. Дебиторка видна по срокам, закрытие месяца — за один день.

Требования

ACC-01MUSTКарточка контрагента из реестра: IDNO, полное наименование, форма, юридический адрес, руководитель, дата регистрации, статус ликвидации, учредители, задолженности перед бюджетом — через Contragenti (контракт XML <counterparty>, INTEGRATION.md §2). Дедупликация строго по IDNO. Дополнительно вручную: банк, IBAN, код НДС, e-mail для документов, договорные условия оплаты (дни, аванс %).

ACC-02MUSTДокументы с нумерацией по типу и году: счёт на аванс, счёт на оплату, накладная (factura fiscală / TTN), акт выполненных работ, счёт-фактура; формируются из заказа/спецификации одной кнопкой, печать в PDF по шаблону Заказчика (ro/ru), выгрузка xlsx. Статусы: черновик → выставлен → оплачен частично → оплачен → аннулирован.

ACC-03MUSTОплаты: загрузка банковской выписки (CSV/XML банков РМ: maib, moldindconbank, Victoriabank), автосопоставление по IDNO и номеру счёта в назначении платежа, ручная привязка остатка; аванс и остаток по заказу/проекту обновляются автоматически (поля advance, paid прототипа — источник истины).

ACC-04MUSTДебиторская и кредиторская задолженность по клиентам и срокам (0–30, 31–60, 61–90, >90 дней), акт сверки за период по контрагенту (PDF/xlsx), напоминания клиентам по шаблону.

ACC-05MUSTНДС и валюты: ставки НДС по номенклатуре (20 %, 8 %, 0 %, освобождено), суммы с НДС/без, курс НБМ на дату документа для валютных договоров (EUR/USD), пересчёт разниц при оплате.

ACC-06MUSTОбмен с учётной системой (1С / una.md): пакетная выгрузка документов и справочников за период (JSON/XML + gzip(SQLite) по образцу хаба hub/), приём статусов проведения и оплат обратно; журнал обмена с ошибками по документу; повторная отправка без дублей (идемпотентность по номеру документа и хешу).

ACC-07SHOULDe-Factura (СФС РМ): подготовка электронной накладной в формате портала и выгрузка файла; подпись — на стороне бухгалтера.

ACC-08SHOULDЗакрытие периода: блокировка изменения документов до даты; изменения после — только через сторно с записью в аудит.

ACC-09NICEРаспознавание входящих счетов поставщиков (PDF) с проверкой контрагента по реестру.

Критерии приёмки

  • Клиент, добавленный через «Создать из реестра», содержит все поля карточки; повторное добавление того же IDNO — «дубликат», второй записи нет (тест-кейс из --selftest прототипа переносится как есть).
  • Выписка из 100 строк демо-банка сопоставляется автоматически не менее чем на 90 %; остаток привязывается вручную не более чем за 2 клика на строку.
  • Отчёт «Дебиторская задолженность» совпадает с суммой неоплаченных документов; акт сверки печатается на ro и ru.
  • Пакет обмена принимается тестовым приёмником (`hub/` прототипа) с кодом 200, повторная отправка того же пакета даёт статус duplicate.

4. Блок 3 — требования коммерческого отдела

Что хочет коммерческий отдел

Не терять обращения, видеть воронку и сроки, делать КП и спецификации за минуты по прайсу и BOM, участвовать в тендерах с контролем дедлайнов, а после подписания — одной кнопкой превращать сделку в заказ и проект, дальше только следить по канбану.

Требования

COM-01MUSTЛиды и источники (сайт, звонок, рекомендация, выставка, реклама, тендерная площадка): форма с сайта и почта в лиды автоматически; конверсия «В клиенты» с созданием клиента из реестра (ACC-01) и переносом контактов; причина отказа обязательна при статусе «Отказ».

COM-02MUSTСделки и воронка: этапы Новая → Предложение → Переговоры → Выиграна/Проиграна (канонические значения прототипа сохраняются), сумма, вероятность, ожидаемая дата, ответственный; канбан с перетаскиванием (как в прототипе); отчёт воронки по менеджерам и источникам за период; сделка без активности 7 дней — подсветка и задача.

COM-03MUSTКоммерческое предложение и спецификация: из номенклатуры и BOM изделия (§5), цена по прайс-листу с уровнями (розница, опт, дилер), скидка с лимитом по роли (OWN-04), срок изготовления из норм производства, PDF по шаблону на ro/ru/en, версии КП; подписанная спецификация «замораживает» цены и сроки.

COM-04MUSTДоговоры: шаблон (поставка, подряд, рамочный), реквизиты сторон из карточек, условия оплаты (аванс %, дни постоплаты), срок, ответственный; статусы «на согласовании → подписан → исполнен»; напоминание об окончании рамочного договора за 30 дней.

COM-05MUSTТендеры: реестр тендеров (номер, площадка, дедлайн подачи, обеспечение, документы), задачи по чек-листу подачи, результат; выигранный тендер → проект со статусом «Договор» (модель проектов прототипа: Тендер → Договор → Аванс → Дизайн → Производство → Сдача → Оплата → Закрыт | Проигран).

COM-06MUSTЗаказ клиента создаётся из выигранной сделки/спецификации одной кнопкой; вид продажа/услуга/производство; для производства автоматически создаётся производственный заказ (§5) и задачи проекта по шаблону шагов (11 шагов прототипа как базовый шаблон, редактируемый по видам изделий).

COM-07MUSTКалендарь и задачи: звонки, встречи, задачи с напоминаниями, сетка месяца с перетаскиванием (прототип), синхронизация с Google/Outlook-календарём (ICS-подписка минимум).

COM-08SHOULDКоммуникации: e-mail из карточки клиента с шаблонами и историей, звонки через IP-телефонию (журнал, запись по ссылке), рассылки по сегментам с отпиской.

COM-09SHOULDКлиентский портал: статус заказа, документы к оплате, акт приёмки с подписью-подтверждением.

COM-10NICEПодсказки ИИ: черновик КП по описанию запроса, рекомендация цены по истории сделок клиента.

Критерии приёмки

  • Сценарий GUI-самотеста прототипа (лид → клиент → сделка «Выиграна» → заказ со строками → проводка → задачи) проходит без модальных окон и расширен шагами: КП → спецификация → договор → тендер → проект.
  • КП с 20 позициями формируется в PDF за ≤ 5 с; цены после подписания спецификации в заказе изменить нельзя без утверждения.
  • Отчёт воронки за месяц совпадает с количеством сделок по этапам в канбане.

5. Блок 4 — требования производства

Что хочет производство

Получать заказ уже разложенным на операции и материалы, видеть очередь по участкам и реальную загрузку, отмечать выполнение с телефона или терминала в цехе, фиксировать брак и простои, и чтобы план (Гант) сам сдвигался при изменении сроков.

Требования

PRD-01MUSTСпецификация изделия (BOM): состав из номенклатуры (материалы, полуфабрикаты, покупные) с нормами расхода на единицу, версии BOM, замена материала с пересчётом стоимости; для изделий под заказ — BOM создаётся из шаблона по виду изделия и уточняется конструктором.

PRD-02MUSTМаршрутная карта: последовательность операций (резка, фрезеровка, гравировка, сборка, покраска, ОТК, упаковка…) с участком, нормо-часами, оборудованием; задачи проекта прототипа становятся операциями с полями plan_start/due_at/hours_plan/hours_fact/depends_on/seq (уже есть в схеме).

PRD-03MUSTПроизводственный заказ (orders.kind = Производство + project_id): статусы Черновик → Подтверждён → В работе → Выполнен → Оплачен/Отменён; при подтверждении резервируются материалы (§6), при выполнении — проводка приходует изделия на склад ГП (правило прототипа PostOrder: производство +stock).

PRD-04MUSTПланирование и Гант: очередь по участкам, загрузка участка в часах на день/неделю, автоматический расчёт дат операций с учётом зависимостей и сменности (5/2, 8 ч; настраивается), перетаскивание в Ганте меняет план (прототип) с проверкой перегрузки участка — предупреждение в строке сообщений.

PRD-05MUSTТерминал участка (веб на планшете/телефоне): список операций на сегодня, «Начал / Завершил», количество годных и брак с причиной, факт часов; без клавиатуры — крупные кнопки, сканер QR с наряда.

PRD-06MUSTБрак и простои: справочник причин, регистрация на операции, отчёт по причинам и участкам за период, стоимость брака по BOM.

PRD-07MUSTОТК: операция контроля обязательна перед сдачей на склад ГП; результат «принято / на доработку» с фото (файл) и подписью контролёра.

PRD-08SHOULDПотребность в материалах: по подтверждённым заказам на горизонт — дефицит с учётом остатков и резервов, заявка на закупку поставщику (контрагент из реестра, тип «Поставщик»).

PRD-09SHOULDПечать наряда/маршрутного листа с QR на каждую операцию; этикетка изделия с QR (серийный номер) для склада и доставки.

PRD-10NICEУчёт машинного времени оборудования (ЧПУ, лазер) через опрос по OPC UA/CSV-лог станка.

Критерии приёмки

  • Демо-набор содержит не менее 10 производственных заказов с BOM и маршрутами; после «Завершил» по всем операциям проводка приходует изделия, остаток на складе ГП растёт ровно на количество годных.
  • Перегрузка участка (сумма нормо-часов дня > фонда) видна в Ганте и в отчёте загрузки; перенос операции в Ганте пересчитывает зависимые (стрелки «после задачи» прототипа).
  • Терминал участка работает на планшете 10" без горизонтальной прокрутки; операция закрывается за ≤ 3 нажатия.

6. Блок 5 — склад готовой продукции и доставка

Что хотят склад и доставка

Точные остатки в реальном времени по местам хранения, резервы под заказы, отгрузка по документам без бумажных журналов, маршруты на день для водителей и статус доставки, который видит менеджер и клиент.

Требования

WHS-01MUSTСклады и места хранения: несколько складов (материалы, полуфабрикаты, ГП, брак), ячейки/зоны; остатки по складу и ячейке; все движения — документы (приход из производства, перемещение, отгрузка, инвентаризация, списание) с проводкой; поле items.stock прототипа становится агрегатом по складу ГП.

WHS-02MUSTРезервирование под подтверждённые заказы; доступный остаток = остаток − резерв; отгрузка сверх доступного невозможна.

WHS-03MUSTОтгрузка: из заказа — задание на комплектацию (чек-лист с QR), накладная/TTN (ACC-02), фиксация даты отгрузки (orders.ship_date — источник этапа «Отгружено» на рабочем столе), контроль долга клиента (OWN-04).

WHS-04MUSTДоставка: рейс на день (транспорт, водитель, порядок точек), маршрутный лист, статусы «в пути → доставлено → отказ/возврат» с фото и подписью получателя в мобильном веб-приложении водителя; клиенту — SMS/e-mail со статусом и ссылкой.

WHS-05MUSTИнвентаризация: ведомость по складу/ячейке, ввод факта со сканера, акт расхождений, корректирующие движения через утверждение.

WHS-06SHOULDУпаковка и весогабариты номенклатуры для расчёта загрузки транспорта и стоимости доставки; перевозчики (внешние) как контрагенты типа «Партнёр».

WHS-07SHOULDВозвраты и рекламации: документ возврата, причина, связь с заказом и ОТК, отчёт по рекламациям.

WHS-08NICEОптимизация маршрута рейса (порядок точек) и трекинг по геопозиции водителя.

Критерии приёмки

  • Отчёт «Остатки номенклатуры» прототипа расширен складами и резервами; сумма остатков по складам равна агрегату; попытка отгрузить больше доступного — отказ.
  • Сквозной сценарий на демо-данных: производственный заказ → приход на склад ГП → резерв → комплектация → TTN → рейс → «доставлено» с фото; на рабочем столе заказ проходит этапы «Готово к отгрузке» → «Отгружено» → «Закрыто» после оплаты.
  • Мобильный экран водителя открывается по ссылке без установки, работает офлайн на время отсутствия сети (очередь статусов).

7.5. Правила разработки (обязательны)

  1. Не переписывать прототип с нуля. Схема, канонические значения, правила этапов, проводки, конверсии, форматы lang.json/processes.json/crm.ini, XML-контракт Contragenti — фиксированы. Изменение любого из них — отдельное решение Заказчика с миграцией и обновлением всех трёх клиентов.
  2. Три похожие строки лучше преждевременного обобщения (PORT_MACOS_ru.md §0.4). Никаких абстракций «на будущее».

  6. Секреты — только переменные окружения / gitignored-конфиги; проверка диффа перед пушем на password=, api_key, Bearer.
  7. Документы обновляются в том же коммите, что и функция (API_ru.md, INSTALL_*, акт тестирования).
  8. Демо-данные обязательны для каждой новой сущности (AGENTS.md §1): реалистичные, десятки записей, все статусы, все плитки непустые; счётчики — в seed.log.
