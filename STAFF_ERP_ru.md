# Сотрудники в Demo CRM и обмен ими с ERP UNIAC/OfficePlus

Документ описывает раздел «Сотрудники» (регистрация людей администратором,
доступ, восстановление пароля), правки карточки задачи по замечаниям к
интерфейсу, отчёт по людям и двусторонний обмен карточками с ERP через
триггеры на обеих сторонах.

Сделано и проверено в macOS-версии (`crm_macos/`, Swift/AppKit). Сторона
ERP — SQL-скрипт `sql/erp_users_sync.sql` и модуль хаба
`hub/users_sync.py`. Перенос на Windows-версию (Delphi) описан в
последнем разделе.

## 2. Раздел «Сотрудники»

Сотрудник и пользователь входа — одна запись (таблица `users`). Заводит
людей администратор; остальные роли видят список, но кнопки записи у них
погашены.

Поля карточки:

| Поле | Колонка | Замечание |
|---|---|---|
| Сотрудник | `full_name` | Переименование переносится в задачи и проекты, иначе отчёт по людям раздваивается. |
| Логин | `login` | Уникален, регистр при входе не важен. |
| Должность | `position` | |
| Роль | `role` | Администратор / Руководитель / Коммерческий / Производство / Склад / Бухгалтерия / Наблюдатель. Права записи в разделе даёт только «Администратор». |
| E-mail, Телефон | `email`, `phone` | Контакты сотрудника. |
| Работает | `active` | Снятый флаг = счёт отключён: человек не войдёт, но остаётся в задачах, проектах и отчётах. |
| Зарегистрирован | `created_at` | Проставляется базой при создании, не редактируется. |
| Пароль | `pass_state` | «стандартный» или «свой» — видно, сменил ли человек выданный пароль. |
| Код в ERP | `erp_code` | `TMS_MUNC.COD` — кадровый код в UNIAC; по нему идёт сверка при обмене. |

**Пароли.** Новый сотрудник получает стандартный пароль `crm2026`
(константа `STANDARD_PASSWORD`); в базе лежит только
`SHA-256("crm:" + логин + ":" + пароль)`. Кнопка **«Сбросить пароль»**
возвращает стандартный и называет его в строке сообщений — это и есть
восстановление доступа. Свой пароль человек ставит в «Настройках», после
чего колонка «Пароль» показывает «свой».

**Защита.** Последнего действующего администратора удалить нельзя. Отказ
во входе называет причину: «нет такого сотрудника», «неверный пароль»,
«счёт отключён администратором».

## 4. Обмен с ERP: одинаковый алгоритм с обеих сторон

Правило взято из самой ERP: изменение ставит в очередь **триггер**, а
очередь разбирает программа. Так же теперь устроена и CRM.

```
   CRM (SQLite)                       хаб (FastAPI)                    ERP (Oracle)
   ───────────────                    ─────────────                    ─────────────
   users                                                               A$ADM / A$ADP / TMS_MUNC
     │ триггеры users_sync_ai/_au/_ad                                    │ триггеры A$ADM$CRM_SYNC_TR,
     ▼                                                                   ▼ A$ADP$CRM_SYNC_TR, TMS_MUNC$CRM_SYNC_TR
   sync_log ──POST /api/v1/users──▶ A$CRM$SYNC.APPLY_USER ─────────────▶ узел пользователя
   users   ◀──GET  /api/v1/users─── A$CRM_SYNC (очередь) ◀───────────────┘
```

**Петли нет.** На обеих сторонах есть «немой» режим: в CRM это флаг
`sync_state.muted`, который проверяет условие `WHEN` каждого триггера, в
ERP — `A$CRM$SYNC.MUTE/UNMUTE`. Принятая строка пишется с выключенной
очередью и обратно не уезжает. DML-тест проверяет это отдельно.

**Пароли не передаются.** В CRM лежит SHA-256, в UNIA — свой код
(`a$util.hide_passwd`). Через обмен идёт только признак «пароль
стандартный, нужна смена»: заведённый из CRM пользователь получает в ERP
свойство `NeedChangePassword = true`, и клиент потребует смену при первом
входе (путь ORA-20050 → `a$util.set_passwd`).

### Соответствие полей

| Demo CRM | ERP UNIAC |
|---|---|
| `users.login` | `A$ADP` KEY `USERNAME` |
| `users.full_name` | `A$ADM.NAME` |
| `users.position` | `A$ADP` KEY `POSITION` |
| `users.role` | `A$ADP` KEY `CRMROLE` (+ `ADMIN = true` для роли «Администратор») |
| `users.email` | `TMS_MUNC.EMAIL` (при известном `USER_SC`) |
| `users.phone` | `TMS_MUNC.KADR_TEL_CELL` |
| `users.active` | `A$ADP` KEY `Enabled` (`true`/`false`) и `A$ADM.DATE_FINAL` |
| `users.erp_code` | `A$ADP` KEY `USER_SC` (= `TMS_MUNC.COD`) |
| `users.created_at` | `A$ADP` KEY `CRMREGDATE` |

Пользователь в UNIA — это узел дерева настроек (`A$ADM`, `OBJ_TYPE = 7`,
`OBJ_SUBTYPE = 0`), а не строка таблицы; свойства лежат в `A$ADP`
(`KEY = UPPER(NAME)`, значение в `SVALUE`). Запись идёт через обновляемые
представления `A$ADM$V` / `A$ADP$V` — тем же путём, что и конфигуратор
uniConf. После правки свойств вызывается штатная проверка узла
`a$util.node_changed(obj_id, name)` — конфигуратор делает ровно этот вызов
для узлов пользователей (`cnfView.cpp`, `AddCheckNode`).

### Установка стороны ERP

```sql
-- от владельца схемы UNIA
@sql/erp_users_sync.sql
SELECT OBJECT_NAME, STATUS FROM USER_OBJECTS
 WHERE OBJECT_NAME LIKE 'A$CRM%' OR OBJECT_NAME LIKE '%CRM_SYNC_TR';
```

Скрипт создаёт очередь `A$CRM_SYNC` с последовательностью, пакет
`A$CRM$SYNC` и три составных (compound) триггера. Составные они не для
красоты: строчный триггер на `A$ADP`, читающий `A$ADP`, упал бы с
ORA-04091 (mutating table), поэтому строки только собираются, а очередь
наполняется на уровне оператора.

### Хаб

`hub/users_sync.py` + две точки входа в `hub/app.py`:

| Метод | Что делает |
|---|---|
| `POST /api/v1/users` | Принимает строки очереди CRM и зовёт `A$CRM$SYNC.APPLY_USER` на каждую. Отвечает `applied`, `created`, `updated`, `errors`, `acks`. |
| `GET /api/v1/users?limit=200` | Отдаёт неотданные строки `A$CRM_SYNC` и помечает их `SENT_AT`. |

Ключ — тот же `X-API-Key`, что и у приёма пакетов.

### Из интерфейса CRM

Кнопка **«Синхронизация с ERP»** в разделе «Сотрудники»: отдаёт свою
очередь, помечает отданное, забирает встречные изменения и применяет их.
Адрес и ключ ERP — «Настройки» (`crm.ini`, секция `[erp]`). Без адреса
кнопка честно говорит, что ERP не настроена.

## 6. Перенос на Windows-версию (Delphi)

В этой правке `crm_delphi/` **не тронут**: собрать и прогнать обязательные
режимы (`--seed-demo`, `--dml-test`, `--gui-test`) без RAD Studio нельзя, а
коммит без них по AGENTS.md §1 не считается завершённым. `lang.json` уже
общий и содержит все новые строки и список ролей `user_role` — на
Windows его править не нужно.

Что нужно сделать в `crm_delphi/` (порядок как в macOS-версии):

     (только показ; обобщённый CRUD такие колонки не пишет — как `fkReadOnly`).

     `PASS_STD = 'стандартный'`, `PASS_OWN = 'свой'`.

     phone, active, pass_state, erp_code, notes, updated_at` + миграции
