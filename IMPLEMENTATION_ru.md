и интеграция с ERP una.md (Oracle).
**Версия решения:** 1.3.7 · **Редакция документа:** 1.0 от 12.09.2026
**Аудитория:** руководитель проекта внедрения, ИТ-администратор, администратор
базы данных, служба информационной безопасности, ключевые пользователи.

| Раздел | Кому в первую очередь |

| 1–3 | Спонсор проекта, руководитель внедрения |

## 1. Резюме для руководства

**Что решается.** Заведение контрагента в учётной системе выполняется вручную:
сотрудник ищет организацию на портале открытых данных, переносит IDNO, название,
юридическую форму, адрес и руководителя, ошибается в символах и заводит дубли.

**Что предлагается.** Настольная утилита ищет организацию в государственном
реестре и возвращает карточку в вызвавшую систему в формате XML; локальная база
накапливает найденное; при наличии ERP найденная организация записывается в
справочник Oracle тремя связанными блоками без ручного ввода.

| Показатель | Было | Ожидается после внедрения |
|---|---|---|
| Время заведения контрагента | 4–7 минут ручного ввода | 30–60 секунд, из них ручного ввода нет |
| Дубли по одной организации | Возникают при разном написании названия | Исключены: сверка по IDNO плюс ограничение в базе |
| Полнота реквизитов | Заполняется то, что успел перенести оператор | Юридическая форма, адрес, руководитель, учредители, задолженность |
| Источник данных | Копирование из браузера | Государственный реестр, дата получения фиксируется в карточке |

**Ресурсы.** Один ИТ-администратор на всё внедрение; администратор базы данных —
только на фазе интеграции с ERP (ориентировочно два рабочих дня); ключевой
пользователь от бизнес-подразделения — на приёмку.

**Сроки.** Базовый вариант (рабочие места без ERP) — от трёх рабочих дней.
Полный вариант с интеграцией и обменом сотрудниками — три-четыре недели,
см. раздел 5.

**Стоимость лицензий:** отсутствует, решение открытое (MIT). Затраты —
рабочее время и, при варианте с общим справочником, один сервер приложений.

## 2. Область внедрения

**Входит в объём работ:**

- установка утилиты Contragenti и Demo CRM на рабочие места (Windows, macOS);
- настройка каталогов данных, языка интерфейса, стартовой базы организаций;
- подключение к учётной системе заказчика через контракт вызова (процесс или
  локальный HTTP-интерфейс);
- при варианте C — запись организаций в справочник ERP una.md (Oracle);
- при варианте D — двусторонний обмен карточками сотрудников с ERP;
- при вариантах B–D — развёртывание хаба сбора баз, TLS, ключи доступа;
- приёмочные испытания по разделу 8 и передача в эксплуатацию.

**Не входит в объём работ:**

- доработка учётной системы заказчика на стороне заказчика (предоставляется
  контракт интеграции и готовые обёртки на Python, C++ и Delphi);
- миграция исторических данных о контрагентах из других систем;
- обход средств защиты портала: форма реестра закрыта невидимой reCAPTCHA, и
  решение работает с ней штатным способом, силами оператора (см. раздел 9);
- поставка и лицензирование Oracle, Google Chrome, Windows и macOS;
- обучение работе с самой ERP una.md.

## 3. Варианты развёртывания

Выбирается один вариант; переход к следующему возможен без переустановки.

| | Вариант | Состав | Кто участвует | Ориентировочный срок |
|---|---|---|---|---|
| **A** | Рабочее место | Contragenti + Demo CRM локально, своя база | ИТ-администратор | 3 дня |
| **B** | Подразделение | Вариант A + хаб сбора баз, общий справочник | ИТ-администратор | +5 дней |
| **C** | Интеграция с ERP | Вариант B + запись организаций в Oracle | ИТ-администратор, DBA | +5–10 дней |
| **D** | Полная | Вариант C + обмен карточками сотрудников | ИТ-администратор, DBA, кадровая служба | +5 дней |

**Как выбрать.** Если учётная система одна и она не на Oracle — вариант A с
подключением через контракт интеграции. Если рабочих мест несколько и нужен
единый справочник — B. Если в организации работает ERP una.md — C. Вариант D
имеет смысл там, где список сотрудников уже ведётся в ERP и его дублирование
в CRM недопустимо.

## 4. Предпосылки и проверка готовности

Проверяется до начала работ. Невыполненный пункт — основание перенести старт.

### 4.1. Рабочее место

| Требование | Значение | Как проверить |
|---|---|---|
| Операционная система | Windows 10 версии 1903 и новее, Windows Server 2019/2022, либо macOS 13+ (Apple Silicon) | `winver` / «Об этом Mac» |
| Google Chrome | Установлен, любая актуальная версия | Портал без него недоступен |
| Свободное место | 500 МБ на программу и базы | — |
| Права | Достаточно прав пользователя; для установки в `Program Files` — запрос администратора | — |
| Доступ в сеть | `date.gov.md`, `data2b.md`, `github.com`, `raw.githubusercontent.com` по HTTPS | `curl -I https://date.gov.md` |
| Python | **Не требуется** для работы программ; нужен только для SDK на Python | — |

> **Политика установки MSI.** Если в домене действует запрет на установку
> пакетов Windows Installer, `msiexec` вернёт код 1625 («The system administrator
> has set policies to prevent this installation»). Это ограничение политики, а не
> дефект решения: используется `Contragenti-<версия>-setup.exe`, он Windows
> Installer не задействует. Проверить политику заранее — задача ИТ-администратора.

> **Устаревшее хранилище сертификатов.** На образах Windows Server, давно не
> получавших обновления, обращение к GitHub может завершаться
> `CERTIFICATE_VERIFY_FAILED`. Мастер настройки автоматически повторяет запрос с
> набором корневых сертификатов из поставки; проверка сертификата при этом не
> отключается.

### 4.2. Хаб (варианты B–D)

| Требование | Значение |
|---|---|
| Сервер | Linux x64, 2 vCPU, 4 ГБ ОЗУ, 40 ГБ диска |
| Среда исполнения | Docker с плагином Compose либо Python 3.12 и systemd |
| Сетевой доступ | Порт 443 снаружи; к Oracle — 1521 из сети сервера |
| TLS-сертификат | На доменное имя хаба; пакеты содержат базу организаций и по открытому HTTP не передаются |
| Резервное копирование | Включён каталог данных хаба в регламент |

### 4.3. Интеграция с ERP (варианты C–D)

| Требование | Значение |
|---|---|
| Версия Oracle | 11.2 и выше |
| Драйвер | 64-битный Oracle Instant Client (`basiclite` достаточно); для 11.2 обязателен «толстый» режим, тонкий режим сервер не поддерживает |
| Учётная запись | Отдельная техническая учётная запись с правами на справочник; персональные учётные записи не используются |
| Права на объекты | `SELECT`, `INSERT`, `UPDATE` на `TMS_UNIVERS`, `TMS_ORG`, `TMS_ORG_ACCOUNTS`; для варианта D — право на создание таблицы, последовательности, пакета и триггеров в схеме |
| Тестовый контур | Обязателен: первичная установка объектов обмена выполняется на копии |

## 5. Фазы внедрения

Каждая фаза завершается результатом, который можно предъявить, и критерием
выхода, который проверяется, а не оценивается.

### Фаза 0. Обследование — 3 рабочих дня

**Задачи:** уточнить вариант развёртывания; составить перечень рабочих мест;
зафиксировать учётную систему, в которую возвращается карточка; согласовать
техническую учётную запись Oracle; проверить пункты раздела 4.

**Результат:** заполненный лист готовности (приложение А), выбранный вариант,
план-график тиража.

**Критерий выхода:** все пункты раздела 4 отмечены как выполненные либо по ним
приняты решения с указанием ответственного и срока.

### Фаза 1. Пилот — 5 рабочих дней

**Задачи:** установить решение на два рабочих места ключевых пользователей;
настроить язык и каталоги данных; подключить вызов из учётной системы;
провести обучение на рабочем месте (1 час на пользователя).

**Результат:** два работающих места, протокол испытаний по разделу 8
(пункты 8.1–8.3).

**Критерий выхода:** самопроверка утилиты — 8 из 8; мастер настройки в режиме
без окна завершается с кодом 0 и итогом «ошибок 0, замечаний 0»; ключевой
пользователь самостоятельно заводит контрагента из реестра.

### Фаза 2. Интеграция — 5–10 рабочих дней (варианты B–D)

**Задачи:** развернуть хаб, выпустить ключи рабочим местам, настроить TLS;
для варианта C настроить подключение к Oracle и проверить запись организации на
тестовом контуре; для варианта D установить объекты обмена сотрудниками.

**Результат:** работающий хаб с дашбордом, протокол испытаний (пункты 8.4–8.6),
запись об установленных объектах в базе.

**Критерий выхода:** проверка живости хаба отвечает успехом; приём без ключа
отклоняется с кодом 401; тестовая организация появилась в справочнике ERP всеми
тремя блоками и повторная отправка дубля не создала; для варианта D правка
карточки сотрудника доходит в обе стороны и не зацикливается.

### Фаза 3. Тираж — по плану, ориентировочно 1 час на рабочее место

**Задачи:** установка волнами по подразделениям; тихая установка допускается
средствами доставки ПО; после каждой волны — выборочная проверка.

**Результат:** реестр рабочих мест с версией и датой установки.

**Критерий выхода:** на всех местах волны установлена одна версия; выборочная
проверка (не менее 10% мест или трёх машин) пройдена.

### Фаза 4. Передача в эксплуатацию — 3 рабочих дня

**Задачи:** передать службе эксплуатации регламент раздела 11; настроить
резервное копирование; согласовать порядок обновлений (раздел 10); закрыть
замечания пилота.

**Результат:** подписанный акт приёмки (приложение В), назначенные
ответственные, заведённые учётные записи поддержки.

**Критерий выхода:** акт подписан, открытых замечаний уровня «блокирующее» и
«существенное» нет.

## 7. Технологические процедуры

Команды приводятся для версии 1.3.7; актуальный номер версии — в файле `VERSION`
репозитория и в манифесте `release.json`.

### 7.1. Установка рабочего места, Windows

Рекомендуемый способ — установщик без Windows Installer. Файл небольшой
(около 12 МБ), полную сборку он скачивает при установке и сверяет контрольную
сумму, поэтому **на время установки нужен доступ в интернет**.

```
Contragenti-1.3.7-setup.exe
```

Тихая установка для средств централизованной доставки:

```
Contragenti-1.3.7-setup.exe /S /D=C:\Program Files\Contragenti --lang ro
```

Дополнительные ключи: `--no-shortcuts` (без ярлыков), `--no-wizard` (не запускать
мастер), `--extract-only <каталог>` (портативная распаковка без записей в реестр).

**Если интернет на рабочем месте отсутствует** либо политика требует MSI:

```
msiexec /i Contragenti-1.3.7-win64.msi /qn
```

Пакет MSI содержит всё необходимое и во время установки ничего не скачивает.
Запускать из сессии с правами администратора, иначе возможны коды 1925 и 1730.

### 7.2. Установка рабочего места, macOS

```bash
curl -fsSL https://raw.githubusercontent.com/PavelTuhari/Contragenti/main/release/contragenti-macos-install.sh | bash
```

Либо пакет `Contragenti-1.3.7-macos.pkg` из каталога `release/`. Приложения не
подписаны сертификатом разработчика, поэтому первый запуск выполняется через
контекстное меню «Открыть».

### 7.3. Мастер настройки и проверка рабочего места

Мастер запускается автоматически после установки, позже доступен из меню «Пуск»
как «Contragenti — настройка и обновление». Он составляет технический паспорт
машины, проверяет Chrome, обновляет компоненты, разворачивает стартовую базу
организаций и выполняет самопроверку.

Проверка без окна, пригодная для журналирования:

```
"%ProgramFiles%\Contragenti\ContragentiSetup.exe" --check --offline --no-seed --no-python --lang ro
```

Код возврата 0 и строка итога «ошибок 0, замечаний 0» — рабочее место принято.
Журнал и отчёт сохраняются в каталоге данных пользователя.

**Каталоги данных.** Программы пишут рядом с собой, если это разрешено; при
установке в `Program Files` — в профиль пользователя. Правило действует и для
администратора, чтобы у разных пользователей не расходились базы.

| Данные | Windows | macOS |
|---|---|---|
| База организаций, настройки | `%LOCALAPPDATA%\Contragenti\` | `~/Library/Application Support/Contragenti/` |
| База Demo CRM, отчёты | `%LOCALAPPDATA%\Contragenti\DemoCRM\` | `~/Library/Application Support/Contragenti/DemoCRM/` |
| Журналы мастера | `%LOCALAPPDATA%\Contragenti\logs\` | `~/Library/Logs/Contragenti/` |

### 7.4. Подключение учётной системы заказчика

Решение вызывается как отдельный процесс и возвращает карточку файлом:

```
Contragenti.exe --pick --out card.xml --lang ru --q "<фильтр>" --no-server --no-tray
```

Три исхода обрабатываются вызывающей стороной: карточка добавлена; организация
уже есть (сверка по IDNO); пользователь закрыл окно без выбора — файла нет, и это
не ошибка. Таймаут ожидания выбора — пять минут.

Для систем, которым удобнее HTTP (в том числе 1С), доступен локальный интерфейс
на `127.0.0.1:9393`: `/pick`, `/open`, `/card`, `/search`, `/health`. Готовые
обёртки вызова — в каталоге `sdk/` (Python, C++) и в `crm_delphi/uContragenti.pas`
(Delphi). Полный контракт — `INTEGRATION.md`.

### 7.5. Развёртывание хаба

Ключи рабочим местам выпускаются заранее, по одному на машину или подразделение:

```bash
python tools/hub_keygen.py "Бухгалтерия" --save
python tools/hub_keygen.py --list
python tools/hub_keygen.py --revoke <ключ>
```

Вариант с Docker (архив Oracle Instant Client для Linux x64 положить рядом с
`Dockerfile`):

```bash
cd deploy
cp .env.example .env          # заполнить пароль технической учётной записи
cp ../hub_config.json .
docker compose up -d
```

Вариант со службой systemd описан в `deploy/README_ru.md`. В обоих случаях хаб
слушает петлевой адрес, наружу его выставляет reverse-proxy с TLS; ограничение на
размер тела запроса должно быть не меньше `max_upload_mb` (по умолчанию 64 МБ).

> **Контроль доступа.** Если хаб слушает внешний адрес, а список ключей пуст,
> приём намеренно отвечает кодом 503. Приём без ключа допустим только на
> локальном стенде.

### 7.6. Подключение к справочнику ERP (варианты C–D)

Параметры подключения задаются переменными окружения либо файлом
`tms_config.json`; окружение имеет приоритет. **Пароль в конфигурационный файл,
попадающий в систему контроля версий, не записывается.**

| Переменная | Назначение |
|---|---|
| `TMS_DSN` | Строка подключения |
| `TMS_USER` | Техническая учётная запись |
| `TMS_PASSWORD` | Пароль (задаётся средствами хранения секретов заказчика) |
| `ORACLE_CLIENT_DIR` | Каталог 64-битного Instant Client |

Организация записывается тремя автономными блоками — справочная запись,
реквизиты, банковские счета. Каждый блок идёт своей транзакцией: недоступность
одного не отменяет остальные. Дубли отсекаются по фискальному коду дважды —
проверкой перед вставкой и ограничением в самой базе.

### 7.7. Обмен карточками сотрудников (вариант D)

Устанавливается от владельца схемы, сначала на тестовом контуре:

```sql
@sql/erp_users_sync.sql

SELECT OBJECT_NAME, STATUS FROM USER_OBJECTS
 WHERE OBJECT_NAME LIKE 'A$CRM%' OR OBJECT_NAME LIKE '%CRM_SYNC_TR';
```

Все объекты должны иметь статус `VALID`. Обе стороны ставят правку в очередь
триггером, а очередь разбирает хаб. Пароли через обмен не передаются: в CRM
хранится необратимый хэш, в ERP — собственное кодирование; передаётся только
признак «пароль стандартный, требуется смена». Подробности и таблица
соответствия полей — `STAFF_ERP_ru.md`.

## 8. Приёмочные испытания

Особенность решения: результат каждой проверки — код возврата, а не мнение
исполнителя. Протокол заполняется фактическими значениями.

| № | Проверка | Команда | Ожидаемый результат |
|---|---|---|---|
| 8.1 | Самопроверка утилиты | `Contragenti.exe --selftest` | `8/8`, код возврата 0 |
| 8.2 | Самопроверка CRM | `ContragentiCRM.exe --selftest` | `CRM self-test: True`, код 0 |
| 8.3 | Рабочее место целиком | `ContragentiSetup.exe --check --offline --no-seed --no-python` | «ошибок 0, замечаний 0», код 0 |
| 8.4 | Операции с данными | `ContragentiCRM.exe --dml-test` | 110 проверок пройдено, код 0 |
| 8.5 | Интерфейс | `ContragentiCRM.exe --gui-test` | 80 из 80 шагов, отчёт `report.html` |
| 8.6 | Живость хаба | `curl -fsS https://<хаб>/api/v1/health` | Успешный ответ со счётчиком очереди |
| 8.7 | Контроль доступа к хабу | Отправка пакета без ключа | Код 401 |
| 8.8 | Приём пакета | Отправка пакета с ключом | Код 202, пакет переходит в состояние «обработан» |
| 8.9 | Запись в ERP | Заведение тестовой организации | Три блока созданы, идентификатор связывает их |
| 8.10 | Отсечение дублей | Повторная отправка той же организации | Вторая запись не создана |
| 8.11 | Обмен сотрудниками | Правка карточки в CRM и в ERP | Изменение дошло в обе стороны, повторного обмена не возникло |
| 8.12 | Бизнес-сценарий | Заведение реального контрагента ключевым пользователем | Карточка в учётной системе, реквизиты совпадают с реестром |

подписания акта.

**Классификация замечаний.** Блокирующее — сценарий 8.12 не выполняется;
существенное — не проходит любая из проверок 8.1–8.11; несущественное — замечания
к удобству, устраняются в рабочем порядке и не препятствуют приёмке.

## 9. Информационная безопасность и соответствие

**Характер данных.** Сведения об организациях — публичные данные
государственного портала открытых данных. Персональные данные появляются в двух
местах: фамилии руководителей и учредителей в карточке организации (публикуются
самим реестром) и карточки сотрудников заказчика при варианте D.

**Обязательные меры:**

| Мера | Реализация |
|---|---|
| Секреты вне кода | Пароли и ключи — в переменных окружения либо хранилище секретов; файлы с секретами исключены из системы контроля версий |
| Разграничение доступа к хабу | Персональный ключ на рабочее место, отзыв ключа не затрагивает остальные |
| Защита канала | Хаб публикуется только через TLS; прямой доступ к порту приложения закрыт |
| Разграничение ролей в CRM | Роли от «Наблюдателя» до «Администратора»; право заводить сотрудников — только у администратора |
| Парольная политика | Новый сотрудник получает стандартный пароль и обязан сменить его при первом входе; в базе хранится необратимый хэш |
| Отключение вместо удаления | Уволенный сотрудник помечается неактивным: вход закрыт, история задач и проектов сохраняется |
| Журналирование | Журнал мастера настройки, реестр пакетов хаба, очереди обмена — источник для разбора инцидентов |
| Техническая учётная запись | Отдельная запись для записи в справочник, с минимально необходимыми правами |

**Ограничения, о которых заказчик уведомляется письменно:**

1. Форма государственного портала защищена невидимой reCAPTCHA. Решение работает
   с ней штатным способом — управляя браузером от имени оператора; при появлении
   проверки её проходит человек. Средства автоматического обхода не применяются
   и не поставляются.
2. Исполняемые файлы не подписаны сертификатом издателя. При первом запуске
   возможны предупреждения операционной системы и браузера. Подлинность
   проверяется сравнением контрольной суммы с манифестом `release.json`.
3. При варианте D карточки сотрудников передаются между системами внутри
   периметра заказчика. Основание обработки и сроки хранения определяет
   заказчик как оператор персональных данных.

## 10. Управление изменениями и обновлениями

| Способ поставки | Для кого | Как обновляется |
|---|---|---|
| Установщик и MSI | Рабочие места Windows | Повторная установка поверх; данные пользователя не затрагиваются |
| Пакет и установочный скрипт | Рабочие места macOS | Мастер заменяет приложения целиком |
| Мастер настройки | Все рабочие места | Сравнивает версию с манифестом и докачивает компоненты |
| Обновление из репозитория | Места, работающие из исходного кода | Автоматическая проверка при запуске и по команде меню; применяется только при отсутствии локальных правок |

**Правила:**

- версия едина для всех компонентов и зафиксирована в манифесте вместе с
  размером и контрольной суммой каждого файла;
- обновление продуктивного контура выполняется в согласованное окно, после
  проверки на одном рабочем месте;
- откат — установка предыдущей версии тем же способом; пользовательские данные
  лежат отдельно от программы и переустановкой не затрагиваются;
- изменения объектов базы данных (вариант D) устанавливаются сначала на тестовом
  контуре, с фиксацией в журнале изменений схемы.

## 11. Эксплуатация

### 11.1. Регламентные действия

| Периодичность | Действие |
|---|---|
| Ежедневно | Контроль живости хаба и глубины очереди по дашборду |
| Еженедельно | Просмотр пакетов в состоянии «ошибка», разбор причин |
| Ежемесячно | Проверка актуальности версий на рабочих местах; выборочная проверка 8.1 и 8.3 |
| Ежеквартально | Проверка восстановления из резервной копии на тестовом контуре |
| При кадровых изменениях | Отзыв ключа рабочего места, отключение учётной записи сотрудника |

### 11.2. Резервное копирование

| Что | Где | Комментарий |
|---|---|---|
| Каталог данных хаба | Сервер хаба | Реестр заданий и принятые пакеты; достаточен для восстановления службы |
| Базы рабочих мест | Профиль пользователя | Накопленный справочник и данные CRM; включаются в обычный регламент резервного копирования рабочих станций |
| Справочник ERP | Oracle | Штатный регламент базы данных заказчика |

Архивы обработанных пакетов удаляются автоматически по истечении заданного срока
хранения (по умолчанию 14 дней); реестр заданий сохраняется, по нему видна
история приёма.

### 11.3. Типовые обращения

| Симптом | Действие |
|---|---|
| «The system administrator has set policies to prevent this installation» | Ограничение политики на MSI. Установить версией `setup.exe` (раздел 7.1) |
| `CERTIFICATE_VERIFY_FAILED` в журнале | Устаревшее хранилище сертификатов. Мастер переключается на набор из поставки автоматически; при повторении — обновить систему |
| Поиск не возвращает результат, окно ждёт | Проверить, не показана ли проверка reCAPTCHA в окне браузера; её проходит оператор |
| Организация не найдена в реестре | Часть действующих организаций портал не отдаёт; используется второй источник, он включается переключателем «Источники» |
| Хаб отвечает 503 с упоминанием ключей | Ключи клиентов не заданы, приём закрыт намеренно. Выпустить ключи (раздел 7.5) |
| Пакет в состоянии «ошибка» | Открыть журнал задания; типичная причина — недоступность базы данных, пакет переотправляется автоматически |
| Программы не обновляются на рабочем месте | Проверить доступ к репозиторию; при работе из исходного кода обновление не применяется, если есть локальные правки |
